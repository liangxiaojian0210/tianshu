## 需求清单

| # | 需求 | 来源 |
|---|---|---|
| 1 | fan-in 门差值 +120-130ns 的主项是编译侧 join 并发契约（原子输入环 + 单飞锁），而金标准单线程驱动免费跳过同步——对比不等价 | 直槽轮归因 + 用户裁定（2026-09-17） |
| 2 | 「同语义」必须包含**并发语义**：DSL 声明每源一线程（ADR-0021），金标准须付同样的同步代价 | 用户裁定 |

## 决策

### D1：fan-in 三方驱动 = 每源一线程

gold / interpreted / compiled 的 fan-in 驱动统一为每源一线程（对齐声明的运行时语义）；线性与 fan-out 形状单源单线程，不变。

### D2：金标准 join 补手写同步

HandJoin 每状态转移持 `std::mutex`；血缘根经 pending 槽**锁内交接**（根与消息分离暂存，无锁窗口会消费到陈旧根——正确性修复）；发射回调在持锁下执行，锁序固定 j1 → j2 → sink（join 的 dispatch 同步触发下游，无反向取锁路径）。双侧 sink 捕获加锁（融合输出可由任一生产者线程触发）。std::mutex 是「合理手写」的代表性选择（与 CacheBuffer 的 std::mutex 一致）。

### D3：线程化形状的尾巴解读

盾（2 逻辑核）为单线程形状设计；线程化 fan-in 在禁闭下 p99/p999 由调度时间片主导（实测三方同量级 ~3.3ms），为环境项。门比较以 p50 为实现项依据；若未来需要线程化形状的正式 p99 判决，需加宽盾或另行定义线程化协议（待议）。

## 后果与实测（盾内三轮 + 无盾对照）

- **p50 反转**：gold 4338ns（mutex 竞争下 futex 睡眠/唤醒塌缩）vs compiled **371ns**（原子 inbox + 单飞锁从不睡眠）——编译侧**快 11.7×**（盾内）；无盾 1222 vs 912，快 1.3×，方向一致。interpreted 线程化后 992（流水线化反低于单线程 1393）。
- **门判定**：fan-in 自本轮起无超额开销（编译侧更快）；框架 join 机器对合理手写同步是**净优势**而非代价——原 +120-130ns「差距」的实质是不等价比较。
- 负面：金标准复杂度上升（锁序契约、pending 交接）；线程化形状基准噪声增大（调度尾），取数轮次需更多。
